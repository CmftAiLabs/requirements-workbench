# 需求沟通：直接回应与深入评估

更新：2026-11-13。此文同时记录实施范围、判断规则与验收方案。

## 目标与范围

一个可见的需求助手，按需使用 PM、业务分析、UX 三种视角。保持现有九字段、真人采纳、业务确认、版本及交付机制。普通交流不固定展开三专家讨论；AI 共识不等于业务事实或确认。

采用 BMad Party Mode 的 session 思路（一个模型在共同上下文中结合多个角色），不是三个独立模型验证。当前是应用内独立编写的适配规则，不安装或执行整个 BMAD 工作流。方法版本为 `requirements-session-v1`，指引位于 `server/expert-policy.ts`。来源参考：[BMAD 模式说明](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/customize/run-multi-agent-discussions.md)、[角色说明](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/reference/skills-and-agents.md)，查阅日期 2026-11-13。后续若直接引入上游文件，应固定提交并保留对应许可；本版本没有自动跟随上游更新。

## 处理程度的判断

先应用现有确定性规则：不处理本期外、概要卡、冻结交付或未采纳的正式变更；过滤纯致谢；已有等待问题时只接受指定人员的明确回答。随后在现有旁听或对话路由调用中同时生成处理判断和轻量回复，不另设一次专门分类调用。

| 结果 | 条件 | 输出 |
| --- | --- | --- |
| quiet | 收到、致谢、无新事实，或在与真人继续交流且无关键风险 | 保持安静，不制造追问 |
| direct | 依据足够的解释；局部明确补充；一个可直接询问的事实缺口 | 短回复，或一个关键问题 |
| deep / explicit | 用户明确要求多视角、专家评估 | 发起评估 |
| deep / conflict | 能指出具体相互冲突的规则或人员意见 | 发起评估并说明矛盾 |
| deep / tradeoff | 多个可行方案实质影响本期范围、成本或用户任务 | 发起评估并说明待取舍点 |
| deep / coupled_rules | 本轮变化牵动权限、流程、数据或异常，影响尚未明确 | 发起评估并说明关联影响 |

文字长、包含“权限”等词、缺少一个日期，都不能单独触发 deep。多视角请求的否定或引用由模型结合语义判断，不用关键词直接决定评估。服务端要求 deep 有具体原因和非空触发类别，并清除轻量阶段提前生成的结论、追问及整理指令。

例：截止改为周五通常 direct；截止还没定直接问日期；补报名不受名额限制但必须符合场地容量，需澄清规则关联，可 deep。已有材料或回答已明确时不要重复问。

## 深入评估的输出

通过同一个模型完成一轮 session 分析，可按需用现有只读证据工具检索。只展示有贡献的视角，不强制凑齐三个，不制造争论。每个视角最多一条意见：

- PM：目标、价值、范围、优先级、成功标准。
- 业务分析：规则、权限、数据、流程、异常、依赖、验收。
- UX：用户任务、理解成本、状态反馈和失败恢复。

### 三种视角的完整职责

2026-11-13 扩充 `server/expert-policy.ts` 中共用的 `expertPerspectives`，深入评估与字段建议整理都使用这份定义。角色定义包括分析目的、检查方法、真人职责边界和输出约束；不改变 session 执行方式或报告结构，方法版本仍为 `requirements-session-v1`。

| 视角 | 分析职责 | 需要形成的判断 |
| --- | --- | --- |
| 产品经理 PM | 从方案追溯用户问题、场景与结果；区分价值依据与假设；检查本期边界、最小可用闭环、优先级、依赖及成功标准；比较真实可行方案 | 为什么值得做、最小做到哪里、方案影响是什么、还缺哪个关键决定 |
| 业务分析师 | 还原当前做法与期望变化；识别各方诉求和既定规则；检查事件、角色、对象、输入输出、状态、正常/边界/异常路径；核对数据、权限、流程和验收一致性 | 哪条规则缺失或矛盾、适用条件是什么、证据在哪里、如何验证结果 |
| UX 设计师 | 从入口到完成及失败恢复检查任务旅程；核对信息架构、术语、操作顺序、主次层级、界面状态、反馈、输入保留和恢复；在本期平台范围内检查键盘、焦点、标签、对比度等可访问性 | 用户在哪一步遇到什么阻碍、建议如何改善、付出什么代价、如何收集反馈验证 |

各视角只检查本轮相关职责，职责完整不代表每轮逐项汇报。用户明确要求整卡检查时才扩大范围；不为填清单制造问题，不强制凑齐三个观点，也不增加模型调用。真实材料和已有回答优先，缺少依据时区分待验证假设、可选建议及待决定事项，不能编造数据、研究、用户画像或测试结果。方案收益和代价同样需要区分依据与估计，不能在未知时断言“无成本”或“最醒目”，也不能把常见设计惯例或他人的疑虑转述为已有需求规则。

追问由同一个需求助手统一组织，每轮只选一个会改变结论的关键点，并使用调用方的正式追问结构。产品经理真人负责范围、优先级与方案取舍；负责具体场景的业务人员提供规则和使用反馈，业务负责人统一业务分歧。三个AI视角不成为群内追问对象，不代替真人采纳或确认。已有等待问题及明确转题仍遵守当前会话机制。

例如“把蓝色提交按钮改红色以便更醒目”：PM判断是否影响既定目标和范围，不能一律要求重新审批；业务分析核对是否存在已明确的颜色含义或约束；UX比较对比度、尺寸、位置或颜色方案，说明对识别与错误提示区分的影响。现有信息已足够时直接给建议，确需反馈时问原业务诉求人，不宣布某个颜色已被采纳，也不虚构统一视觉规范。

## 评估卡片与展开内容

1. 轻量判断选择 deep 后，在发起深度模型调用前保存 running 卡片，显示“正在为您评估需求”、本次具体原因和可继续发言的提示。
2. 完成后原 ID 的卡片更新为 completed，默认显示结论和当前关键追问。不会连续发送三位专家的气泡。
3. “查看分析依据与不同意见”使用原生可键盘展开控件，展开：为什么评估、专家意见、方案与取舍、仍待明确、本次参考范围、原文依据。材料引用可查看原文。
4. 全卡同时只等待一个问题，问题复用原 FollowUp，既可点选方案也可自由回答；在评估卡片中显示后，不在时间线重复显示第二套控件。
5. failed 显示安全错误与“按最新讨论重试”。重试评估当前讨论，不重放过期答案。
6. superseded 表示运行期间依据变化，旧结果未采用；队列重新判断最新讨论，仍需 deep 时复用同一任务卡片。新内容可以简化为直接回应，不强制继续深评。
7. 已完成的历史评估保留，后续发言或正文变化后标明是此前讨论的评估。

## 数据与执行路径

- `DiscussionAnalysis` 与 `ConversationRoute` 增加可选 handling。旧记录和旧模型测试数据仍可读取。
- `Card.assessments` 保存评估生命周期和报告，独立于消息数组及需求正文。状态更新不增加消息数量，不使既有字段建议因展示更新而失效。
- 附件路径仍保存原有材料回应关联，使用 assessmentId 让前端合并显示，保留附件处理记录；最终响应与评估结果在一个项目事务中保存。
- 复杂附件在评估后额外完成一次材料处理，明确禁止再次进入深评，用于保留独立新卡候选和有依据的当前卡补充；不能因升级评估而丢掉原有材料整理能力。
- 分析依据包含讨论、需求修订、人工决定、材料内容和项目卡片范围。业务状态变化时，服务端拒绝写入旧报告或问题。仅追加普通聊天时，先用轻量语义判断检查是否与当前评估相关：闲聊、致谢、进度询问不丢弃评估；相关规则、范围、约束或追问回答变化才重新判断；明确取消评估则标为 cancelled，不落报告。否定取消、业务申请取消不能误判为取消评估。分类期间再次有消息到达会重新核对，提交时仍做事务内基线检查。
- 评估任务重试有稳定 ID，状态更新不产生重复卡片；不由 AI 自己的输出触发自动循环。
- 进程重启把未完成评估标为失败，原材料与发言保留。
- “整理讨论”共用三视角检查职责，在现有调用里检查完整流程和遗漏，不额外启动三次专家调用。字段建议仍走原校验与人工采纳。
- 单个局部问题优先一次轻量调用；深评额外一次分析。原有字段整理、工具检索、格式修复可能增加实际调用，不能承诺整轮总是一次。

## 实施与验证

实现顺序：判断规则和类型 → 报告/证据校验 → 生命周期与过期控制 → 队列接入 → 卡片与展开 → 回归。

自动化应覆盖：普通回应不发起深评、deep 需有效原因、问题不重复显示、指定回答人规则、伪造/AI 引用拒绝、单模型报告角色唯一、开始/完成/失败/过期、进度不改变业务状态、并发业务补充丢弃旧报告、闲聊保留原评估、明确取消与否定取消、分类期间再来业务消息、重试与重启、附件回应和人工采纳不受破坏。

界面检查覆盖运行中/完成/失败、展开收起、选项及自由回复、长结论与引用、桌面和窄屏。保持键盘访问、自然换行与材料原文入口。

模型质量另用六类真实场景比较：明确局部补充、已有材料答案、单一事实缺失、权限联动、人员冲突、完整需求无须追问。关注有效遗漏、重复追问、无依据结论、回复长度和耗时。自动化验证结构与流程，不代表真实模型必然正确判断所有业务场景。

第一版不引入多模型、多 Agent 并行、专家投票或专家审批；不因检查失败而自动通过确认。按实际试用结果再决定是否扩展独立专家或报告历史分页。


### 闲聊期间的评估与恢复

- 界面不再用“最后一条人类消息变化”宣告评估过期；普通闲聊不显示“讨论已更新”。历史报告在需求修订变化时提示其版本较旧。
- 失败/过期卡片可按最新讨论重试原问题。重试携带 assessmentId，保留原始问题关联，使用最新字段、材料与业务讨论，避免最后一句闲聊抢走评估主题；不会恢复旧结果或自动采纳字段。
- 语义分类只在评估期间有新普通消息时调用；附件、历史编辑、人工决定和业务状态仍走严格基线校验。取消在当前模型返回后核对，不保证立即中断网关生成或计费。
- 回归覆盖无关消息、相关补充、取消、分类竞态和原问题恢复；模型合成验证覆盖天气晚饭、不要取消、明确取消、业务规则变化及取消业务动作。

### 按具体问题核对解决建议

字段修改与问题关闭独立：同一字段的品牌长度缺口，不阻塞采购平台已明确规则的字段草稿。当问题的关联字段在修改前或修改后包含缺口时，服务端额外批量核对原问题全部子项、具体结论、真人依据和最终字段。只有本问题确已落实、且无关未决规则保留，才提供该问题的解决建议。

本问题仍未决或核对失败时，仅移除该问题的解决建议，独立有效的字段草稿继续供人工审核；原问题保持未解决。若检测到无依据删除或掩盖未决规则，则拒绝不安全的草稿。核对结果绑定原问题、结论、引用、角色与精确关联字段内容，前后端采纳校验共用；人工调整后不能复用旧核对。整卡确认仍要求真正缺口全部明确。

提示只解释本问题及相关缺口，不再附加无关的“待确认状态”通用说明。对旧建议缺少问题级核对的情况，提示重新整理，并说明可先单独审核字段修改。

### 按问题性质分配追问

- 使用场景与诉求原因：先问原业务诉求人；具体业务规则问负责该场景的业务人员。业务口径有分歧时由业务负责人统一。
- 本期范围、优先级和成本取舍：产品经理决定；该意见不代表业务规则已确认或所有成员已同意。
- 按钮颜色、布局、提示方式等设计问题：先给可比较的建议，再向相关业务方收集使用反馈；有足够依据后由产品组织方案取舍。普通设计微调不一律升级为范围审批或深入评估。
- 模型通过 `replyRequest` 标记需要回答的人与问题性质，并产生同对象的正式 `question`。只在正文点名要求决定、没有正式追问的输出会进入校正。允许同一轮保留建议回复和正式追问。
- 产品已经表达不同意见并征询大家时，不重复催产品决定；优先询问原业务诉求人。追问与回答均不自动修改正文、采纳或整卡确认。

### 等待问题期间切换业务话题

旧问题未回答时默认继续等待。若最新真人发言明确转向另一项业务诉求，模型可用 `deferQuestion` 引用旧问题和最新消息并说明转题依据，同时给出新正式追问。校验先检查转题依据，不先删除新追问再检查接收人。缺少转题说明时，原输出进入现有一次自动修正流程。

旧问题标记为 `deferred`（暂缓、尚未回答），保留在讨论记录；原接收人仍可定向回复。暂缓问题不会被视为已解决，也不绕过当前修订的整卡确认检查。回复暂缓问题不挤掉另一条当前等待的追问。任何失败均不写入半成品，讨论任务只向用户显示可重试的通俗提示，不暴露内部校验文字。

### 短答和未点击选项的自然回复

讨论监听不设最短字数。当前接收人的回复优先结合等待问题处理；纯寒暄在没有待回答语境时仍可安静处理。模型获得 `answerCandidate`（原问题、完整选项和该接收人的最新消息），不能因为没有 `replyTo` 或带 `@Agent` 就漏记答案。

精确选项匹配，以及二选一的明确纳入问题中唯一对应的肯定/否定短答，可由服务端保守纠正模型的 `quiet + answer:null` 输出。疑问语气、其他成员、过期问题、含义不明或不能唯一对应选项的发言不自动判定。证据始终保留真实原文，允许一个字的人类引用。登记问题回答会提供回执，但不自动写入字段或替代整卡确认。
