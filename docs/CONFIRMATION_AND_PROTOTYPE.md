# 确认与原型更新规则

## 人工决定

- Agent 无字段修改、无待核对事项、无问题解决建议时，结果作为普通回应，不要求产品经理再点采纳，也不阻挡人工确认。旧版本遗留的空建议在启动时修复，迁移可重复执行。
- 有实际修改或问题解决建议时，仍由产品经理采纳；业务负责人单独确认。未采纳的内容可以用于标明待采纳的原型预览，不写入正式卡片或正式 PRD。
- 已确认需求出现新追问时，保留已确认状态，并提示等待回复。只有人采纳修改或明确纳入问题，才使相应确认失效、项目回到可讨论。未确认卡片的待答问题仍阻挡确认。

## 原型更新

- 概要卡全部字段、具体卡归属及有效字段共同参与更新判断。项目、模块和模型输入使用相同概要上下文，旧产物不能因忽略公共约束而被标为已同步。
- 未归类的具体卡共用一个原型模块；按业务模块分类后，才按模块生成。
- Agent 为项目生成统一业务数据定义，明确实体字段、状态、单据关联及虚构初始数据。各模块使用同一数据定义和内存状态，不能各自维护同类单据与库存。
- 数据定义为模块生成阶段的只读输入。定义变化会使相关缓存失效；接口不变时允许复用未改变模块。代码生成与交互检查通过后才发布，失败保留旧原型。

## ERP 验证范围

使用既有海岳精密 ERP 的四份材料和采购、仓储、库存三张具体卡，验证采购申请、分级审批、分批入库、库存及在途更新。模拟业务操作不连接真实采购、支付或财务服务。需求确认测试使用产品经理与业务负责人的独立身份，并记录采纳前、采纳后和重新确认的版本。
